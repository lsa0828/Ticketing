# Ticketing Web Application
공연 예매의 전 과정을 구현한 Spring 기반 티켓 예매 웹사이트입니다.
- 좌석 예약, 결제 및 환불 로직 설계 및 구현
- JMeter 기반 부하 테스트로 커넥션 지연 현상 확인 및 해결
- 낙관적 락 적용으로 DB 부하 낮추며 동시 요청 충돌 제어

### 프로젝트 개요
기간: 2025.10 ~ 2025.11

참여자: 1명

기술 스택: Java, Spring, JSP, JavaScript, CSS, MySQL

로컬 실행 환경: Tomcat 10

### 주요 기능
회원 기능
- 로그인/회원가입
- 예매/환불 내역 조회

예매
- 공연 좌석 조회 및 선택
- 예매 진행 시 좌석 상태 AVAILABLE -> BOOKING -> SOLD로 순차적 업데이트
- 중복 예매 방지를 위한 트랜잭션 처리

결제
- 카카오페이(외부 결제 연동)/쿠폰/포인트 결제 병합 처리
- 결제 시 포인트 차감 및 쿠폰 상태 변경 (NOT-USED -> USED)

환불
- 예약번호 기반 환불 요청 -> 쿠폰 및 포인트 상태 복구
- 공연 시작 전까지만 환불 가능하도록 제한

### 핵심 경험
1. 동시성 테스트를 통한 DB 병목 및 동시성 문제 분석

   부하 테스트로 병목 구간을 식별하고 커넥션 풀과 낙관적 락 적용하여 동시성 처리 구조를 개선했습니다.

   - 문제 발견
     - 동시 요청을 50명부터 단계적으로 증가시키며 부하 테스트 진행
     - 200명부터 Error 16%가 발생하며 오류율이 급증
     - 약 150까지 안정적으로 처리되고 이후부터 요청 처리에 한계가 나타남
   
   - 1차 원인 분석: DB 커넥션 생성 병목
     - HTTP 요청마다 DB 커넥션을 새로 생성하는 구조에서 동시 요청 증가 시 커넥션 생성 병목 및 타임아웃 발생
     - 이로 인해 요청이 DB에 충분히 도달하지 못해 실제 동시성 문제가 가려지고 있음을 확인
     - HikariCP 커넥션 풀 적용으로 커넥션 생성 병목 해소
  
   - 2차 원인 분석: 동시성 제어 과정의 경쟁 조건
     - 커넥션 풀 적용 후 실제 동시 요청이 DB에 도달하면서 기존 조건부 UPDATE 방식의 경쟁 조건을 확인
     - 동일 좌석에 대한 UPDATE가 동시에 실행될 경우 복수 요청이 모두 성공할 수 있는 가능성 확인
     - UPDATE 이전에 별도의 SELECT로 락을 선점하지 않는 구조였기 때문에, 트랜잭션 타이밍에 따라 요청 간 경쟁이 발생

   - 해결 및 비교
     - 동시성 제어를 위해 낙관적 락과 비관적 락을 각각 적용하여 성능 비교
     - 낙관적 락 적용 결과: 1000명 테스트 Error 0%. 평균 응답 시간은 약 10ms (200명 기준)
     - 비관적 락 적용 결과: 1000명 테스트 Error 1.10%. 낙관적 락 대비 평균 응답 시간 약 2배
     - 성능 및 동시성 처리 결과를 비교하여 낙관적 락 최종 적용
    
2. 트랜잭션 및 데이터 조회 구조 개선

   - Facade 패턴 적용
     - 예매 과정에서 분산되어 있던 여러 작업을 하나의 트랜잭션으로 통합
     - 예매 처리 과정의 원자성 보장
    
   - N+1 문제 개션
     - N+1이 발생하는 조회 구간을 분석하고 JOIN 기반 쿼리로 변경
     - 반복적인 DB 조회를 줄여 데이터 조회 효율 개선
    
   - UI 전용 DAO 분리
     - 화면에 필요한 복합 조회 로직을 별도의 DAO로 분리
     - 조회 로직과 비즈니스 로직의 결합도를 낮추고 역할을 명확하게 구성
    
3. 개발 생산성 개선

   - Shell Script + IntelliJ External Tools 연동
     - Tomcat 빌드 및 실행 과정을 스크립트로 자동화
     - 반복적인 빌드·배포 작업을 단순화하여 로컬 개발 편의성 향상
